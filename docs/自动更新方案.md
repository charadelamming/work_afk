# 自动更新方案（GitHub Releases）

> 用 `tauri-plugin-updater` 从 GitHub Release 的 `latest.json` 读取新版本，下载 NSIS 安装包、校验签名、静默覆盖安装，然后重启进程。
>
> **这不是热更新**：安装时必须退出进程（Windows 会锁住正在运行的 exe），用户看到的是「程序消失两秒又回来」，不是「界面不重启就换了代码」。

| 项目 | 内容 |
| --- | --- |
| 当前版本 | `0.1.0`（尚无任何更新机制） |
| 目标版本 | `0.1.1` 先跑通链路，`0.2.0` 作为首个正式版 |
| 方案状态 | 已定方案，**代码尚未改动** |
| 关键依赖 | `tauri-plugin-updater` 2.x、`tauri-plugin-process` 2.x、`tauri-apps/tauri-action@v0` |
| 适用平台 | 仅 Windows x64（NSIS、currentUser 安装） |

## 0. 这份文档怎么用

1. 新开一个对话，第一句话可以直接说：**「按 `docs/自动更新方案.md` 第 9 节的任务清单，从 Step 1 开始做，每完成一步告诉我改了什么、怎么验证」**。
2. 第 **10 节**是必须先拍的板（仓库地址、公开/私有、要不要镜像）。没定之前不要动代码。
3. 第 **9 节**的每一步都写了「改哪里 / 怎么改 / 怎么验证」，**不要跳步**——签名、版本号、capabilities 任何一处漏了，表现都是「检查不到更新」，很难反查。
4. 第 **8 节**的坑是真会踩的，实施前通读一遍。

## 1. 为什么选这个方案

| 方案 | 做法 | 用户体验 | 本期结论 |
| --- | --- | --- | --- |
| 冷更新（本方案） | 下载新安装包 → 验签 → 静默安装 → 重启 | 进程退出约 1–3 秒，窗口位置/配置保留 | ✅ 采用 |
| 前端整包热更 | 远程拉 `dist/` 覆盖本地资源，`location.reload()` | 看起来无缝，但推错就白屏，且没有回滚 UI | ❌ 不做 |
| 手动发版 | 群里发新 exe，用户自己覆盖 | 用户不会升级 | ❌ 现状，要改 |

**为什么不做前端热更**：这个项目的业务逻辑（计薪引擎 `src/core/pay.ts`）全在前端。热更等于「把一份没有签名、没有回滚、没有灰度校验的代码直接塞进用户机器上跑」；一旦推错版本，用户打开就是白屏，而小组件是常驻托盘的后台程序，白屏后连入口都没有，只能卸载重装。收益（省一次重启）远小于风险。

**明确不在本期做的事**：

- 不做前端资源热更 / 不做运行时脚本下发。
- 不做灰度发布（GitHub 静态 JSON 没有分流能力）。
- 不做「回滚到旧版」按钮（回滚只能靠发一个版本号更高的旧代码）。
- 不改 `productName`（会换安装目录与开始菜单项，收益为零）。
- 不引入服务器、不做自己的更新 API。

## 3. 整体链路

```text
你 push 一个 v0.1.1 的 tag
        │
        ▼
GitHub Actions（windows-latest）
   ├─ 构建 NSIS 安装包
   ├─ 用私钥签名 → 产出 setup.exe.sig
   └─ 建 Release，上传 exe / sig / latest.json
        │
        ▼
用户机器（已安装 0.1.0 的版本）
   1. 启动或定时：GET releases/latest/download/latest.json   ← 一个 302 到静态文件
   2. 比较 version（0.1.1 > 0.1.0）
   3. 下载 setup.exe，用内置公钥验签
   4. 静默运行安装器 → 当前进程退出 → 覆盖安装 → 拉起新 exe
   5. 新进程启动，版本变 0.1.1，config.json 与窗口位置原样还在
```

**这是一个「静态文件 + 签名」的模型**：GitHub 只负责托管三个不会变的文件，没有任何服务端逻辑；安全性完全由「公钥在客户端编译进二进制 + 下载后验签」保证。所以即使文件被中间人替换、或者换了一个不可信的镜像站，装不进去——验签会失败。

## 4. 关键约定

### 4.1 固定 endpoint

```text
https://github.com/<OWNER>/<REPO>/releases/latest/download/latest.json
```

`releases/latest` 是 GitHub 的**稳定指针**，永远指向「最新的、已发布（published）且非 prerelease」的那个 Release。它不随版本号变化，所以这个 URL 可以硬编码进程序，永久不用改。

⚠️ 三个失败姿势：Release 存成 **draft**、勾了 **prerelease**、仓库是**私有**——三者都会让这个 URL 返回 404，而客户端的表现只是「检查不到更新」，不会有任何报错弹窗。

### 4.2 `latest.json` 结构

每个 Release 里都要放一份，内容随版本走：

```json
{
  "version": "0.1.1",
  "notes": "见 更新记录.md",
  "pub_date": "2026-11-11T10:30:00Z",
  "platforms": {
    "windows-x86_64": {
      "signature": "dW50cnVzdGVkIGNvbW1lbnQ6...（.sig 文件全文，单行）",
      "url": "https://github.com/<OWNER>/<REPO>/releases/download/v0.1.1/重生之我挂机上班_0.1.1_x64-setup.exe"
    }
  }
}
```

- `version` 必须和安装包里 `tauri.conf.json` 的 `version` 完全一致，否则会出现「下完装完还是提示有更新」的死循环。
- `url` 用**带 tag 的固定地址**（`releases/download/v0.1.1/...`），不要用 `latest/download/...`，否则以后老版本会下到新包。
- `signature` 是 `.sig` 文件的**全部内容**，必须用脚本序列化，手写极易破坏换行/转义。
- `pub_date` 用 UTC 的 ISO8601。

### 4.3 签名

- 私钥（`*.key`）**只存在于**两处：你的离线备份 + GitHub Secrets。
- 公钥写进 `tauri.conf.json` 的 `plugins.updater.pubkey`，**编译进二进制**，是唯一的信任锚点。
- 私钥丢了 = 已经装出去的老版本永远收不到更新（只能让用户手动重装），所以生成后立刻做离线备份。
- 换公钥需要「一代过渡」：先用旧私钥发一个内含新公钥的版本，等用户都升到这版，之后才能换。

### 4.4 版本号

发版前同步改三处，并保持一致：

```text
package.json                 "version": "0.1.1"
src-tauri/Cargo.toml         version = "0.1.1"
src-tauri/tauri.conf.json    "version": "0.1.1"     ← updater 只认这个
```

`Cargo.lock` 会跟着 `Cargo.toml` 自动更新，不用手改。

## 5. 一次性配置（改代码的部分）

### 5.1 生成签名密钥（只做一次）

```powershell
pnpm tauri signer generate -w "$env:USERPROFILE\.tauri\reborn-work.key"
```

会要求输入一个密码（记进密码管理器），然后打印公钥（`dW50cnVzdGVk...` 开头的一长串）。

- 把 `reborn-work.key` **复制到 U 盘 / 加密网盘**做离线备份。
- 公钥粘贴到下一步的 `plugins.updater.pubkey`。
- 两个值都不进仓库：`.key` 绝不能提交，公钥进配置是可以的。

> 该命令产出的是 minisign 格式密钥，`tauri-plugin-updater` 原生支持，不需要额外的 GPG / 证书。

### 5.2 打开签名产物开关

`src-tauri/tauri.conf.json` 的 `bundle` 段加一行：

```json
{
  "bundle": {
    "active": true,
    "targets": ["nsis"],
    "createUpdaterArtifacts": true,
    "...": "其余保持原样"
  }
}
```

开启后每次构建都会在安装包旁边多出一个 `重生之我挂机上班_0.1.1_x64-setup.exe.sig`。

### 5.3 配置 updater 插件

还是 `src-tauri/tauri.conf.json`，在顶层加 `plugins`（若已有则合并）：

```json
{
  "plugins": {
    "updater": {
      "pubkey": "dW50cnVzdGVkIGNvbW1lbnQ6...此处粘贴 5.1 生成的公钥",
      "endpoints": [
        "https://github.com/<OWNER>/<REPO>/releases/latest/download/latest.json"
      ],
      "windows": {
        "installMode": "passive"
      }
    }
  }
}
```

- `installMode`：`passive`（默认，显示系统进度条）／`quiet`（完全无界面）／`basicUi`（NSIS 向导）。小组件推荐 `passive`，用户至少看到一点动静，不会以为程序挂了。
- `endpoints` 是**数组**，按顺序尝试：第一个失败自动试第二个。国内可以把 OSS / 自建静态地址加成第二项（见第 10 节）。
- `pubkey` 一旦发布就**不能随便换**，见 4.3。

### 5.4 加依赖

`src-tauri/Cargo.toml`：

```toml
[dependencies]
tauri-plugin-updater = "2"
tauri-plugin-process = "2"
```

`package.json`（前端）：

```bash
pnpm add @tauri-apps/plugin-updater @tauri-apps/plugin-process
```

> 版本跟随 `@tauri-apps/api` 的 2.x 系列即可，不要手动指定到 3.x。

### 5.5 注册插件

`src-tauri/src/lib.rs`，在 `tauri::Builder::default()` 之后、`.manage(...)` 之前串上去：

```rust
tauri::Builder::default()
    .plugin(tauri_plugin_updater::Builder::new().build())
    .plugin(tauri_plugin_process::init())
    // ...原有 .plugin(...) / .manage(...) / .setup(...)
```

### 5.6 放行权限

`src-tauri/capabilities/default.json` 的 `permissions` 数组追加：

```json
"updater:default",
"process:allow-restart"
```

漏了这两个，前端 `check()` 会抛 `not allowed`，且日志里只有一行 `permission denied`。

## 6. 客户端交互设计

### 6.1 检查策略

| 时机 | 行为 |
| --- | --- |
| 启动后 10 秒 | 静默检查一次（不弹窗、不阻塞启动、失败只写日志） |
| 每 24 小时 | 静默检查一次（小组件常驻托盘，可能几天不重启） |
| 用户点「检查更新」 | 立即检查，**无论结果如何都要有反馈**（无更新也要提示「已是最新」） |

节流用 `localStorage` 记 `lastUpdateCheckAt`，避免频繁启动把 GitHub 打爆。

### 6.2 交互落点

- **设置页**「关于」区域加一行：`版本 0.1.0 [检查更新]`，点击后就地展示状态（检查中 / 已是最新 / 发现 v0.1.1 / 下载 43% / 重启以完成更新 / 失败原因）。
- **托盘菜单**在「设置」下方加「检查更新」，点击后：打开设置页并 `emit` 一个事件，让设置页执行同一套检查逻辑。
- **悬浮窗不放任何更新 UI**：380×212 的透明卡片没有空间，也容易误触。

### 6.3 下载与安装分两步

`tauri-plugin-updater` 的 JS API 提供三种组合，本项目用后两种组合出的「后台下载 + 用户确认后安装」：

```ts
await update.downloadAndInstall(cb)   // 一步到位，适合无 UI 场景
await update.download(cb)             // 只下载，进度可控
await update.install()                // 装已下载的包（会退出进程）
```

原因：小组件是常驻程序，用户可能正在看工资数字，不能「点一下检查就自己重启了」。所以流程是：

```text
发现新版本 → 后台自动下载（进度显示在设置页）
           → 下载完成，提示「v0.1.1 已就绪，重启即可完成更新」
           → 用户点「立即重启」→ install() → relaunch()
```

### 6.4 平台层代码骨架

新增 `src/platform/updater.ts`（遵循项目约定：**只有 `src/platform` 直接调 Tauri**）：

```ts
import { check, type Update } from '@tauri-apps/plugin-updater'
import { relaunch } from '@tauri-apps/plugin-process'

export type UpdateState =
  | { kind: 'idle' }
  | { kind: 'checking' }
  | { kind: 'none' }
  | { kind: 'available'; version: string; notes: string }
  | { kind: 'downloading'; percent: number }
  | { kind: 'ready'; version: string }
  | { kind: 'error'; message: string }

let pending: Update | null = null

/** 检查更新。浏览器预览环境返回 null，不抛错。 */
export async function checkForUpdate(): Promise<Update | null> {
  try {
    pending = await check({ timeout: 15_000 })   // 复用单例，避免重复下载
    return pending
  } catch (err) {
    console.warn('[updater] 检查失败', err)
    return null
  }
}

/** 后台下载，返回是否成功。 */
export async function downloadUpdate(onPercent: (p: number) => void) {
  if (!pending) return false
  let total = 0
  let got = 0
  await pending.download((event) => {
    if (event.event === 'Started') total = event.data.contentLength ?? 0
    if (event.event === 'Progress') {
      got += event.data.chunkLength
      onPercent(total ? Math.round((got / total) * 100) : 0)
    }
  })
  return true
}

/** 安装并重启。必须在用户确认后调用。 */
export async function installAndRelaunch() {
  if (!pending) return
  await pending.install()
  await relaunch()
}
```

`settings` 页的调用侧要点：

- 组件卸载时**不要**取消下载（用户可能关掉设置页去干活，下载应继续）。
- `pending` 必须是模块级单例，重复点「检查更新」要复用同一个 `Update` 对象，否则会重复下载。
- 所有调用都包 `try/catch`，把 `err.message` 显示成人类可读的一句话。

### 6.5 托盘入口

`src-tauri/src/lib.rs` 的 `build_tray()`（`lib.rs:181`）里，把菜单项追加在「打开设置」之后：

```rust
// lib.rs:182-185 已有一组 MenuItem，照同样写法加一行
let check_update = tauri::menu::MenuItem::with_id(app, "check_update", "检查更新", true, None::<&str>)?;

let menu = MenuBuilder::new(app)
    .item(&show)
    .item(&settings)
    .item(&check_update)      // ← 新增
    .item(&hide)
    .separator()
    .item(&quit)
    .build()?;
```

在 `on_menu_event`（`lib.rs:199`）里加分支，注意 `"settings"` 分支用的是项目已有的 `spawn_settings_window`（`lib.rs:139`），不要另造函数：

```rust
"check_update" => {
    let _ = app.emit("check-update", ());   // 需要 use tauri::Emitter;
    spawn_settings_window(app.clone());     // 把设置页叫到前面，用户才看得到结果
}
```

前端在 `SettingsApp.vue` 里 `listen('check-update', runCheck)`，与点击「检查更新」走完全相同的函数。

> 注意：`emit` 是广播给所有窗口的，悬浮窗也会收到，`listen` 只在设置页注册即可。

## 7. 发版流程

### 7.1 路线 A：GitHub Actions（推荐，长期用）

见附录 A 的完整 workflow。日常只有三步：

```bash
# 1. 改三处版本号（见 4.4）+ 写 更新记录.md
# 2. 提交
git add -A && git commit -m "release: v0.1.1"
# 3. 打 tag 并推送
git tag v0.1.1 && git push origin v0.1.1
```

推上去约 8–15 分钟（首次冷缓存更久），Release 自动出现，附带 `exe`、`exe.sig`、`latest.json`。

**前置条件**（一次性）：

1. 仓库 Settings → Secrets and variables → Actions 加两条：
   - `TAURI_SIGNING_PRIVATE_KEY`：`.key` 文件的**全文**
   - `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`：生成时设的密码
2. 仓库 Settings → General → 确认 Actions 允许运行。
3. `GITHUB_TOKEN` 无需手动建，workflow 里声明的 `permissions: contents: write` 会赋权。

### 7.2 路线 B：本地构建 + `gh` 上传（首次验证用这个）

先手动跑一遍，确认「链路」和「签名」都对，再接 CI——出错时排查范围小得多。

```powershell
# 1. 版本号改成 0.1.1（三处）
# 2. 注入私钥（当前会话有效）
$env:TAURI_SIGNING_PRIVATE_KEY = Get-Content "$env:USERPROFILE\.tauri\reborn-work.key" -Raw
$env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD = "你的密码"

# 3. 构建（会同时产出 .exe 和 .exe.sig）
pnpm tauri build

# 4. 生成 latest.json（用脚本，别手写）
pwsh -File scripts\make-latest-json.ps1 -Tag v0.1.1 -Owner <OWNER> -Repo <REPO>

# 5. 上传
gh release create v0.1.1 `
  "src-tauri\target\release\bundle\nsis\重生之我挂机上班_0.1.1_x64-setup.exe" `
  "src-tauri\target\release\bundle\nsis\重生之我挂机上班_0.1.1_x64-setup.exe.sig" `
  "latest.json" `
  --title "v0.1.1" --notes "见 更新记录.md" --latest
```

生成脚本见附录 B（也可先手写一次，确认字段都对，再固化成脚本）。

> 若 `TAURI_SIGNING_PRIVATE_KEY` 没设，构建会直接失败并提示 `signing requires a private key`——这是好事，比发出去一个没签名的包强。

### 7.3 发布后 30 秒自检

```powershell
# 应返回 302 或 200，且内容是刚发的 JSON
curl.exe -I https://github.com/<OWNER>/<REPO>/releases/latest/download/latest.json
curl.exe -s https://github.com/<OWNER>/<REPO>/releases/latest/download/latest.json
```

## 8. 坑清单

| 坑 | 现象 | 处理 |
| --- | --- | --- |
| 存成 draft / 勾了 prerelease | `releases/latest` 返回 404，客户端「检查不到更新」 | Release 必须 **published + 非 prerelease** |
| 私有仓库 | 下载 `latest.json` 需要 token，客户端没有 | 仓库必须 **public**（代码可以只放源码，Release 也可用公开的空仓库） |
| 三处版本号不同步 | 装完仍提示有新版本 / 关于页版本对不上 | 发版前 `package.json`、`Cargo.toml`、`tauri.conf.json` 一起改 |
| `latest.json` 被 CDN 缓存 | 发了新版，部分用户几小时后才看到 | GitHub 对 release 附件默认 `Cache-Control: no-cache`；若自己加镜像，务必也设 no-cache |
| 中文产物名 | URL 变成 `%E9%87%8D%E7%94%9F...`，`gh` 上传和部分代理会出问题 | 能跑就先不动；实在要改，用构建后重命名脚本，**不要改 `productName`** |
| 同名 asset 重复上传 | HTTP 422 `already_exists` | 先 `gh release delete-asset` 或直接删 Release 重建 |
| 免安装版用户 | 收到更新提示但装不上 | **发布版不再提供免安装 exe**（第 10 节第 3 条）；本地构建出的 `reborn-work.exe` 不传 Release |
| 断网 / GitHub 被墙 | 启动卡住几秒 | `check()` 传 `timeout`，整体 `try/catch`，失败静默；不要 `await` 在窗口创建前 |
| 私钥丢失 | 老用户永久收不到更新 | 离线备份 + 密码管理器双份 |
| `identifier` 被改 | 升级后配置全丢（新目录） | `com.rebornwork.app` 永远不改 |
| CI 里少了 `contents: write` | tauri-action 建 Release 403 | workflow 顶层声明 `permissions` |
| macOS 打包问题 | 本项目不涉及 | 只构建 `--bundles nsis`，不要加 `dmg`/`app` |

## 12. 附录

### 附录 A：`.github/workflows/release.yml`

```yaml
name: Release

on:
  push:
    tags:
      - 'v*'

permissions:
  contents: write

jobs:
  publish:
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v4

      - uses: pnpm/action-setup@v4
        with:
          version: 12

      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: pnpm

      - uses: dtolnay/rust-toolchain@stable

      - uses: swatinem/rust-cache@v2
        with:
          workspaces: src-tauri -> target

      - run: pnpm install --frozen-lockfile

      # 门禁；若拖慢发布可删掉，但建议保留
      - run: pnpm check

      - uses: tauri-apps/tauri-action@v0
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          TAURI_SIGNING_PRIVATE_KEY: ${{ secrets.TAURI_SIGNING_PRIVATE_KEY }}
          TAURI_SIGNING_PRIVATE_KEY_PASSWORD: ${{ secrets.TAURI_SIGNING_PRIVATE_KEY_PASSWORD }}
        with:
          tagName: ${{ github.ref_name }}
          releaseName: 'v__VERSION__'
          releaseBody: '详见 docs/更新记录.md'
          releaseDraft: false
          prerelease: false
          args: --bundles nsis
```

要点：

- `tagName: ${{ github.ref_name }}` 直接复用你推的 tag，不再让 action 自己造 tag。
- action 默认会把 `latest.json` 一并生成并上传（`includeUpdaterJson` 默认开启），所以**不需要**再手工生成。
- `releaseDraft: false` + `prerelease: false` 必须显式写，否则老版本 `releases/latest` 会 404。
- 想重跑某次发布：Actions 页面点 **Re-run jobs**，不要重复推同一个 tag（会冲突）。

### 附录 B：`scripts/make-latest-json.ps1`（本地路线用）

```powershell
param(
  [Parameter(Mandatory)] [string] $Tag,      # v0.1.1
  [Parameter(Mandatory)] [string] $Owner,
  [Parameter(Mandatory)] [string] $Repo,
  [string] $BundleDir = "src-tauri\target\release\bundle\nsis"
)

$ErrorActionPreference = 'Stop'

$conf = Get-Content "src-tauri\tauri.conf.json" -Raw | ConvertFrom-Json
$setup = Get-ChildItem $BundleDir -Filter *.exe | Select-Object -First 1
if (-not $setup) { throw "找不到安装包：$BundleDir" }

$sigPath = "$($setup.FullName).sig"
if (-not (Test-Path $sigPath)) { throw "找不到签名：$sigPath（构建时是否设置了 TAURI_SIGNING_PRIVATE_KEY？）" }

$sig = (Get-Content $sigPath -Raw).Trim()
$url = "https://github.com/$Owner/$Repo/releases/download/$Tag/$($setup.Name)"

$payload = [ordered]@{
  version   = $conf.version
  notes     = "详见 docs/更新记录.md"
  pub_date  = (Get-Date).ToUniversalTime().ToString("yyyy-MM-ddTHH:mm:ssZ")
  platforms = [ordered]@{
    "windows-x86_64" = [ordered]@{ signature = $sig; url = $url }
  }
}

$json = $payload | ConvertTo-Json -Depth 6
[IO.File]::WriteAllText((Join-Path $PWD "latest.json"), $json, (New-Object System.Text.UTF8Encoding($false)))
Write-Host "已生成 latest.json：version=$($conf.version) url=$url"
```

说明：

- 用 `[IO.File]::WriteAllText` + 无 BOM UTF8，避免 `Out-File` 写 BOM 导致 JSON 解析失败。
- `signature` 直接取 `.sig` 原文，`ConvertTo-Json` 会自动处理换行转义——**不要手写 JSON**。
- 中文文件名会原样进 `url`，GitHub 侧能处理；若用 `gh` 上传后 404，把文件名改成 ASCII 再试。
