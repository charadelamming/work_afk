# 发版流程（维护者视角）

> 一句话：**改三处版本号 → 提交推送 → 打 tag 推送**。CI 自动跑测试、签名出包、生成 `latest.json`、发 Release，全程约 6 分钟。
>
> 你不需要在本地打包，也不需要装 GitHub CLI 或命令行传文件。

---

## TL;DR（复制粘贴版）

```powershell
# 1. 改三处版本号（见下节表格），然后：
git add -A
git commit -m "chore: 0.1.3"
git push origin main

# 2. 打 tag 并推送（tag 必须带 v，且与版本号一致）
git tag v0.1.3
git push origin v0.1.3
```

等 6 分钟 → 自检 → 完事。

---

## 0. 前置条件（一次性，已完成）

- 仓库 `Settings → Secrets and variables → Actions` 里有两个 secret：
  - `TAURI_SIGNING_PRIVATE_KEY`：私钥文件全文（含首行 `untrusted comment:`）
  - `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`：私钥密码
- ⚠️ **私钥离线备份**：`C:\Users\admin\.tauri\reborn-work.key` + 密码，拷到 U 盘和密码管理器。
  私钥丢了就再也发不出老用户能自动升级的包（换密钥 = 老版本不认新公钥，只能让所有人手动重装）。

---

## 1. 改版本号（三处，必须完全一致）

| 文件 | 位置 | 改成 |
| --- | --- | --- |
| `package.json` | 第 4 行 `"version"` | `0.1.3` |
| `src-tauri/Cargo.toml` | 第 3 行 `version =` | `0.1.3` |
| `src-tauri/tauri.conf.json` | 第 4 行 `"version"` | `0.1.3` |

**为什么三处**：前端读 `package.json`、Rust 编译读 `Cargo.toml`、而**自动更新只认 `tauri.conf.json`**——只改一处，用户会永远「检测到新版」却装不上。

漏改不会造成事故：CI 第一步就会拿 tag 和 `tauri.conf.json` 比对，不一致直接失败。

改完建议顺手在 `docs/更新记录.md` 顶部加一条（格式：`## YYYY-MM-DD` + `### N. 标题` + **现象/原因/修改/验证**）。

## 2. 提交并推送

```powershell
git add -A
git commit -m "chore: 0.1.3"
git push origin main
```

## 3. 打 tag 并推送（这一步才真正触发发版）

```powershell
git tag v0.1.3
git push origin v0.1.3
```

| 要求 | 违反的后果 |
| --- | --- |
| tag 必须 `v` 开头 + 三段的语义化版本 | 不带 `v` 不会触发 workflow |
| tag 版本号 = `tauri.conf.json` 的 version | CI 第一个校验步骤失败 |
| tag 之前 `main` 已推上去 | CI 会检出 tag 指向的提交，代码没推就等于发了旧代码 |

## 4. 等 CI（约 6 分钟）

打开 <https://github.com/charadelamming/work_afk/actions> 看最新的 **Release** 运行。会依次看到：

1. 校验 tag 与版本号一致
2. `pnpm install --frozen-lockfile`
3. 门禁 `pnpm check`（类型 + 计薪断言 + 变异测试 + 100 个单测）
4. 出包（带签名，约 4 分钟）
5. 生成 `latest.json`（同时把安装包改成 ASCII 名）
6. 发布 Release

全绿即成功。**红了先看是哪一步**：环境/网络抖动（如拉取依赖失败）→ 该运行右上角 **Re-run failed jobs**；代码真有问题 → 改完提交，发一个**更高的版本号**（新 tag），不要强改或删除已推的 tag。

## 5. 自检（1 分钟）

```powershell
# 客户端真正请求的那个地址，必须能返回新版本号
curl.exe -sL "https://github.com/charadelamming/work_afk/releases/latest/download/latest.json"
# 看到 "version": "0.1.3" 就对了
```

（`curl.exe` 是 Windows 10/11 自带；若习惯 PowerShell 原生，也可用 `(Invoke-RestMethod ".../latest.json").version`。）

再去 Releases 页面确认三个资产齐全：

- `reborn-work_0.1.3_x64-setup.exe`（约 1.4MB）
- `reborn-work_0.1.3_x64-setup.exe.sig`（460B 单行）
- `latest.json`（约 1KB）

`latest.json` 里 `url` 必须与资产名**逐字一致**，`signature` 不能为空。

## 6. 用户什么时候收到

发完之后，已经装着 0.1.1 / 0.1.2 的用户：

- **自动**：启动 10 秒后查一次，之后每 24 小时一次；新版**后台静默下载**，下完才提示「v0.1.3 已就绪，重启应用即可完成更新」
- **手动**：托盘右键 →「检查更新」，或 设置 → 关于 → 检查更新

你自己这台也一样。想立刻验证，就在那台机器上点「检查更新」，几秒钟就能装完。

> 装过 **0.1.0** 的机器收不到任何自动更新（那一版还没接 updater），必须手动装一次 0.1.1 以上。

## 7. 红线：这些事不能做

| 不能 | 原因 |
| --- | --- |
| 勾 **Pre-release** | `releases/latest` 会跳过预发布，用户永远收不到 |
| 发**更低**的版本号 | updater 只升不降，老用户不会收到 |
| 发完想改资产 / 重打同名 tag | 仓库开了 immutable releases，发布后资产和 tag 都锁死 |
| 发了坏包指望撤回 | 唯一可行的补救是**尽快发下一个版本**（0.1.4）修掉 |
| 改了代码却没改版本号 | 版本号相同 = 客户端认为已是最新，用户拿不到 |

## 8. 出问题怎么办

| 现象 | 处理 |
| --- | --- |
| CI 在「校验 tag 与版本号一致」失败 | 三处版本号和 tag 不一致，改完发新 tag（如 v0.1.4） |
| CI 在「门禁」失败 | 本地跑 `pnpm check` 修完，提交后重打一个更高的 tag |
| CI 在「出包」失败 | 多半是 secrets 缺失/失效，检查两条 Actions secrets |
| CI 其他步骤失败 | Actions 页面 → 该运行 → 右上 **Re-run failed jobs**，同一个 tag 重跑 |
| tag 打错了但还没推 | `git tag -d v0.1.3`，改完重打 |
| tag 已经推上去但提交错了 | 不要强行改 tag，直接发下一个版本号 |
| 发完发现 `latest.json` 版本号不对 | 因为有签名校验，坏包装不上，用户只会看到失败提示；修好发下一版即可 |

## 附：本地验证（可选，发版不依赖）

```powershell
# 想先本地确认能打包成功（需要签名密钥环境变量）
$env:TAURI_SIGNING_PRIVATE_KEY = Get-Content "$env:USERPROFILE\.tauri\reborn-work.key" -Raw
$env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD = "<密码>"
pnpm tauri build --bundles nsis
```

产物在 `src-tauri/target/release/bundle/nsis/`。本地打的包**不要**手工上传——CI 会用同样的流程出包，手工上传容易出现版本号和 `latest.json` 不一致。

CI 不可用时的兜底流程见 [运行与打包手册](运行与打包手册.md) 第 5.2 节。
